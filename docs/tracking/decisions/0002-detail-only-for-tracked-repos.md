# 0002. 비싼 상세 정보는 고정 + 보고 있는 저장소만 받는다

## 맥락

GitHub API 요청 한도는 토큰당 시간 단위로 정해져 있다(GraphQL 시간당 5000점, REST 시간당 5000회). 메인테이너는 수십~수백 개 저장소에 쓰기 권한이 있다. 저장소마다 최근 커밋 7개와 CI, 릴리스, 기여자, 언어, 최근 30일 스타 시각(REST 여러 페이지)을 5분마다 받으면 한도를 금방 넘는다. 한도를 넘으면 목록·알림까지 멈춘다.

## 결정

저장소를 두 단계로 나눈다.

- 모든 내 저장소: 머리글(이름·스타·열린 수·푸시 시각 등)과 열린 PR·이슈 목록만 받는다.
- 상세 추적 저장소 = 고정 저장소 + 지금 상세 화면에 열린 저장소 1개: 커밋·CI·릴리스·기여자·언어·스타 시각을 받는다.

남은 한도가 10% 미만이면 상세 추적 갱신부터 미룬다. 상세 화면에 들어갈 때의 즉시 갱신만은 한도가 적어도 한다.

## 다른 선택지

- **모든 저장소의 상세를 순회(라운드 로빈)**: 저장소 수가 많으면 한 바퀴가 몇 시간이 걸려 정보가 늘 오래된다. 그래도 한도는 계속 쓴다. 검토했으나 기각했다.
- **화면을 열 때만 받기(캐시 없음)**: Home의 실패한 CI·스타 변화 카드를 만들 수 없고 오프라인에서 보여 줄 것이 없다.
- **웹훅·서버로 모으기**: 앱에 서버가 없고 만들지 않는다.

## 결과

- Home의 "실패한 CI"(a)와 "스타 변화" 카드는 상세 추적 저장소만 대상이다. 고정하지 않은 저장소의 기본 브랜치 CI가 깨져도 Home에 나오지 않는다. 사용자는 이 제약을 알고 골랐다.
- 고정 개수가 사실상 한도 사용량을 정한다. 고정을 수십 개 하면 상세 갱신이 자주 미뤄진다.
- 상세 화면을 처음 열면 잠깐 머리글만 보이다가 상세가 채워진다.
- 캐시에 없는 저장소(검색 결과)도 숫자 ID로 상세를 받아 같은 화면에 보여 줄 수 있다.
