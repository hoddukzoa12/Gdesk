# 0010. Home 최근 커밋은 커밋 검색으로 받는다

## 맥락

Home에 "내 최근 커밋" 다섯 줄을 보이기로 했다. 커밋은 저장소마다 흩어져 있어 내가 커밋한 저장소를 먼저 알아야 한다. 흔한 방법은 사용자 Events API(`GET /users/{login}/events`)의 `PushEvent`에서 커밋 목록을 읽는 것인데, GitHub는 2025-10부터 `PushEvent` 페이로드에 커밋 목록을 싣지 않는다. 이벤트만으로는 푸시가 있었다는 사실과 브랜치·SHA 범위만 안다.

## 결정

REST 커밋 검색 `GET /search/commits?q=author:<내 로그인>&sort=author-date&order=desc&per_page=5` 한 번으로 받는다. 목록 주기 끝과 `home` 수동 새로고침 때 받고, 결과는 캐시 표에 통째로 바꿔 쓴다. "모두 보기"는 같은 조건의 GitHub 커밋 검색 페이지를 연다.

## 다른 선택지

- **Events + compare**: 푸시 이벤트마다 `GET /repos/{o}/{r}/compare/{before}...{head}`를 불러 커밋을 채운다. 다섯 줄을 위해 요청이 푸시 수만큼 늘고(core 한도), 기능 브랜치·강제 푸시 범위를 따로 다뤄야 한다. 이벤트 API 자체도 최근 90일·300개로 잘린다.
- **상세 추적 저장소의 커밋 목록 모으기**: 이미 받는 기본 브랜치 커밋 7개를 합친다. 고정하지 않은 저장소의 커밋이 빠지고, 내 커밋이 아닌 것을 걸러야 한다.
- **GraphQL `contributionsCollection.commitContributionsByRepository`**: 저장소별 커밋 수만 주고 커밋 메시지·SHA가 없다.

## 결과

- 요청은 갱신마다 1번이지만 search 자원(작은 분당 한도, 다른 자원과 따로 셈)을 쓴다. 자동 갱신은 search 자원이 적으면 최근 커밋만 건너뛴다.
- 커밋 검색은 기본 브랜치만 색인하고 몇 분 늦다. 기능 브랜치에만 있는 커밋, 방금 푸시한 커밋은 보이지 않는다. 화면은 이 한계를 받아들이고 따로 보완하지 않는다.
- 작성자 이메일이 내 GitHub 계정에 연결되지 않은 커밋은 `author:` 검색에 나오지 않는다.
- 로그인 이름을 모르면 요청하지 않는다.
