# 풀리지 않은 문제

## 윈도우 HTTPS 클론의 askpass와 취소 정리가 확인되지 않았다

- **현상**: 윈도우에서 HTTPS 클론은 임시 `.bat` askpass가 지연 확장(`!GDESK_GIT_TOKEN!`)으로 토큰을 출력하는 방식이다. 이 경로와, 취소했을 때 git 프로세스 종료를 기다린 뒤 만든 폴더를 지우는 경로가 윈도우에서 한 번도 실행되지 않았다. 단위 테스트는 맥에서만 돌았고, CI의 윈도우 작업은 화면 테스트를 돌리지 않는다.
- **영향**: 윈도우 사용자는 HTTPS 클론이 인증 실패로 끝나거나, 취소 뒤 파일 잠금 때문에 반쯤 받은 폴더가 남을 수 있다.
- **지금 못 푸는 이유**: 윈도우 실행 환경이 없고, 원격 저장소가 없어 CI 윈도우 작업도 아직 돈 적이 없다.
- **방법**: CI가 처음 돌 때 윈도우 단위 테스트 결과(`src/main/git/*.test.ts`)를 확인하고, 윈도우 기계에서 실제 비공개 저장소 클론·취소를 한 번 해 본다.

## 클론이 진행 중일 때 다른 클론을 요청하면 진행 중인 클론이 취소된다

- **현상**: 클론 대화상자가 진행 중인 상태에서 빠른 검색창의 "저장소 클론" 명령 등으로 `requestClone`을 다시 부르면, 대화상자가 새 저장소로 바뀌면서 앞 클론을 취소한다. 사용자에게 묻지 않는다.
- **영향**: 큰 저장소를 받던 중이면 그동안 받은 내용과 그 클론이 만든 폴더가 말없이 지워진다. 사용자 폴더는 지우지 않으므로 기존 데이터 손실은 없다.
- **지금 못 푸는 이유**: 막을지, 확인을 받을지, 여러 클론을 동시에 보여 줄지는 화면 동작을 정하는 결정이 필요하다.
- **방법**: 진행 중이면 새 요청을 거부하고 진행 중인 대화상자를 다시 앞에 띄우는 것이 가장 단순하다.

## 리눅스에서 임시 폴더가 실행 금지(noexec)면 HTTPS 클론이 실패한다

- **현상**: askpass 스크립트를 `os.tmpdir()` 아래에 만들고 git이 그것을 실행한다. `/tmp`가 `noexec`로 마운트된 보안 강화 리눅스에서는 git이 askpass를 실행하지 못해 인증 실패(`auth_failed`)로 끝날 것으로 보인다.
- **영향**: 그런 환경의 사용자는 HTTPS 클론을 쓸 수 없다. SSH 클론은 영향이 없다.
- **지금 못 푸는 이유**: 그런 환경에서 재현해 보지 않았고, 스크립트를 둘 대안 위치(사용자 데이터 폴더 아래 등)의 권한·정리 정책을 정해야 한다. 지금 `createAskpass`는 위치를 받지 않는다.
- **방법**: `createAskpass`가 폴더를 받게 하고 로컬 서비스가 `<userData>/askpass`를 쓰게 한다.

## SSH 클론이 호스트 키 확인에서 멈출 수 있다

- **현상**: 처음 접속하는 호스트이거나 키에 암호가 있으면 ssh가 터미널 입력을 기다린다. `GIT_TERMINAL_PROMPT=0`은 git 자신의 질문만 막고 ssh 질문은 막지 않는다. `pnpm dev`처럼 터미널에서 띄운 앱은 그 터미널을 기다리며 클론이 끝나지 않는다. 설치된 앱은 터미널이 없어 ssh가 실패하고 `ssh_auth`로 끝날 것으로 보이나 확인하지 않았다.
- **영향**: 사용자가 취소하기 전까지 진행률이 멈춘다.
- **지금 못 푸는 이유**: `BatchMode=yes`를 강제하면 ssh-askpass나 에이전트 입력에 기대는 사용자 설정을 깨뜨린다. 사용자 SSH 설정을 그대로 따른다는 원칙과 부딪치므로 결정이 필요하다.
- **방법**: 일정 시간 진행률이 없으면 "SSH가 입력을 기다리는 중일 수 있음"을 알리고 취소를 권한다.

## 조직 접근 제한 안내가 깜빡일 수 있다

- **현상**: 목록 갱신은 내 저장소 집합을 먼저 받는다. 이 수집이 완전하면 이번에 제한이 나오지 않은 조직의 안내를 지운다. 그런데 내 저장소 목록에 나오지 않는 조직(멤버가 아닌 조직)의 제한은 뒤이은 검색 목록 수집에서야 다시 기록된다. 그 사이 사이드바·배너의 안내가 사라졌다 나타난다.
- **영향**: 표시만 흔들린다. 데이터는 맞다.
- **지금 못 푸는 이유**: 안내를 어느 수집이 소유하고 언제 지울지 설계를 바꿔야 하고, 실제 조직 제한 응답으로 재현한 적이 없다.
- **방법**: 안내마다 기록한 수집 출처를 두고, 같은 출처가 완전한 결과를 냈을 때만 지운다.

## 저장소가 많은 계정에서 목록 갱신이 GraphQL 한도를 많이 쓴다

- **현상**: 들어온 PR·이슈의 근거를 위해 5분마다 내 저장소 전체의 열린 항목을, 항목마다 최근 코멘트·리뷰 50개의 작성자 관계까지 받는다. 저장소 100개 기준 시간당 약 2400점으로 추정한다(시간당 한도 5000점).
- **영향**: 저장소가 수백 개면 한도 부족으로 상세 갱신이 먼저 미뤄지고, 남은 양이 5% 아래로 내려가면 목록 갱신도 멈춘다.
- **지금 못 푸는 이유**: 실제 GitHub 계정으로 점수를 재 본 적이 없다. 주기·묶음 크기·표본 수는 실측이 있어야 정할 수 있다.
- **방법**: 응답의 `rateLimit { cost }`를 기록해 실측하고, 열린 수나 `pushedAt`이 바뀐 저장소만 다시 받는다.

## 상한에 잘린 저장소 범위에 닫힌 항목이 남을 수 있다

- **현상**: 저장소의 열린 PR·이슈가 50개를 넘으면 최근 갱신 50개만 받아 기존 행과 합친다. 받은 범위의 가장 오래된 시각보다 오래된 기존 행은 이미 닫혔어도 지우지 않는다.
- **영향**: 열린 항목이 많은 저장소에서 들어온 목록·응답 없는 새 기여에 닫힌 항목이 섞일 수 있다. 그 저장소의 열린 수가 50 아래로 내려가 범위가 통째로 바뀔 때까지 남는다.
- **지금 못 푸는 이유**: 오래된 행마다 닫힘 여부를 확인하면 요청이 늘어 바로 위의 한도 문제와 부딪친다. 비용과 정확도 사이의 결정이 필요하다.
- **방법**: 남은 행의 노드 ID를 묶어 `state`만 가끔 묻는다.

## 로그아웃 상태에서는 오류 보고 대화상자가 로그인 화면 뒤에 숨는다

- **현상**: 로그인 화면은 `z-[1000]`으로 창 전체를 덮고, 오류 보고 대화상자는 `z-50`이다. 로그아웃·로그인 중에 처리되지 않은 오류가 나면 보고서는 만들어지지만 대화상자가 보이지 않는다.
- **영향**: 로그인 화면에서 난 오류는 보고할 수 없다. 보고서는 `crash:pending`에 남는다.
- **지금 못 푸는 이유**: 오버레이 간 쌓임 순서와 로그인 화면의 `inert` 처리 범위를 함께 정해야 한다. 오류 보고 화면 테스트도 아직 없다.
- **방법**: 오류 대화상자를 로그인 화면보다 위에 두고, 로그인 화면이 `inert`를 걸 때 대화상자 포털은 뺀다. 화면 테스트는 `crash:testTrigger`로 만든다.

## 설치 파일이 Electron 기본 아이콘을 쓴다

- **현상**: `build/`에 아이콘 파일이 없어 맥·윈도우·리눅스 앱이 Electron 기본 아이콘으로 나온다. 저장소 루트에 커밋되지 않은 `Gdesk.png`가 있지만 포장 설정에 연결되어 있지 않다.
- **영향**: 배포하면 사용자에게 Electron 아이콘이 보인다.
- **지금 못 푸는 이유**: 어떤 그림을 공식 아이콘으로 쓸지는 메인테이너가 정한다.
- **방법**: `build/icon.png`(1024px)를 두면 electron-builder가 OS별 아이콘을 만든다.

## 화면 테스트가 시스템 클립보드를 덮어쓴다

- **현상**: 클론 화면 테스트의 HTTPS·SSH 주소 복사가 실제 시스템 클립보드에 쓴다.
- **영향**: 개발자가 테스트를 돌리는 동안 복사해 둔 내용이 사라진다. CI에는 영향이 없다.
- **지금 못 푸는 이유**: Playwright Electron은 클립보드를 격리하지 않는다. 메인의 `clipboard`를 테스트에서 기록용으로 바꿀지 정해야 한다.
- **방법**: `shell.openExternal`처럼 테스트 준비 코드가 `app.evaluate`로 `clipboard.writeText`를 기록용으로 바꾼다.

## 로그아웃 직후 늦게 도착한 일부 응답이 캐시에 쓰일 수 있다

- **현상**: 동기화 엔진의 갱신은 로그아웃·계정 전환 세대(generation)가 바뀌면 캐시에 쓰지 않는다. 하지만 빠른 검색창의 GitHub 저장소 검색 결과 저장(`search.service`)과 로컬 폴더 찾기의 저장소 확인(`local.service`의 `lookupRepo`)은 이 확인을 거치지 않는다. 로그아웃 순간에 이 요청이 진행 중이면 응답이 로그아웃 뒤에 캐시나 연결에 쓰일 수 있다.
- **영향**: 다음 계정으로 로그인했을 때 이전 계정이 검색했던 저장소 한두 개가 캐시에 남을 수 있다. 토큰은 남지 않는다.
- **지금 못 푸는 이유**: 최종 점검에서 동기화 경로만 범위로 고쳤다. 두 경로는 쓰는 위치가 달라 같은 세대 확인을 따로 넣어야 한다.
- **방법**: 두 경로도 요청 시작 때 세대를 기억하고, 쓰기 직전에 `db/cleanup.ts`의 세대와 비교해 다르면 버린다.
